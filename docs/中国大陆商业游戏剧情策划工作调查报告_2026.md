# 中国大陆商业游戏剧情策划工作调查报告

**副标题：岗位边界、端到端生产流程、阶段输入/产出、UE/Unity 引擎落地与 GitHub 工具指南**  
**版本日期：2026-07-24**

---

## 摘要

中国大陆商业游戏团队中的“剧情策划”通常不是一个只负责写对白或故事梗概的纯写作岗位，而是处在**创意、游戏设计、内容生产与技术实现交界处**的复合岗位。不同公司会把职责拆成文案策划、世界观策划、剧情策划、任务策划、叙事演出策划、关卡叙事、编剧、技术叙事、IP 文案等不同岗位；小团队则常由一两个人兼任。

综合近期招聘样本、国内行业文章、国家新闻出版署材料、Epic/Unity 官方文档、GDC 案例与 GitHub 开源项目，可以把商业叙事生产概括为一句话：

> **把“玩家应该感受到什么”逐步转译成“游戏在什么状态下、通过什么玩法和表现、调用哪些资产、向玩家输出什么信息”，再把这一套内容变成可验证、可本地化、可版本管理、可在引擎里运行的数据与资产。**

因此，一名成熟的剧情策划至少需要同时理解三层：

1. **语义层**：世界观、人物、主题、情节、语气和文化包装；
2. **逻辑层**：任务状态、触发条件、分支、变量、失败与回退、奖励和存档；
3. **表现层**：对白 UI、镜头、动画、音频、关卡事件、过场、交互反馈与节奏。

真正稳定的商业管线，不是“写完 Word 文档后交给程序”，而是建立以下四种接口契约：

- **身份契约**：每条任务、节点、台词、角色、镜头、音频有稳定且不可随意更改的 ID；
- **状态契约**：哪些变量由剧情系统拥有，哪些由玩法系统拥有，何时读写；
- **命令契约**：剧情节点可以向引擎发出哪些有类型的命令，参数是什么；
- **资产契约**：文本、配音、表情、动画、镜头、场景和特效如何被定位、加载和替换。

# 1. 调查范围、方法与可信度说明

本报告使用五类材料：

1. **中国大陆招聘样本**：叠纸《无限暖暖》叙事策划、搜狐畅游剧情策划、腾讯 UE 项目任务策划等，用于观察公司对岗位职责的真实描述；
2. **中国游戏行业方法文章**：腾讯游戏学堂等公开内容，用于补充国内团队的常用术语和工作语境；
3. **官方监管与引擎文档**：国家新闻出版署、Epic Games、Unity 官方文档，用于确认审批、数据、本地化、资产和演出能力；
4. **公开生产案例**：GDC、Unreal Fest、IGDA，用于对照大型项目如何建设写作、演出和配音管线；
5. **GitHub 仓库与文档**：用于评估可学习、可原型、可量产的叙事工具和集成方案。

需要注意：

- 中国大陆没有一套所有公司统一采用的“剧情策划国家标准流程”。本报告给出的是**跨公司、跨品类的综合生产模型**；
- 招聘页面只能证明某一时点、某一项目对岗位的要求，不能代表整个行业；
- 商业团队常有自研编辑器、内部数据库、资产平台和自动化工具，公开资料无法完整覆盖；
- 下文将明确区分“行业普遍规律”“引擎官方能力”和“本报告的工程建议”。

# 2. 中国大陆商业团队中的岗位边界

## 2.1 为什么“剧情策划”不是单纯编剧

近期岗位样本反复出现以下职责组合：

- 世界观和剧情结构；
- 任务流程、NPC 行为和玩法编排；
- 把剧本转换成画面、镜头与演出；
- 与美术、程序、关卡、UI、音频、导演协作；
- 进入 UE 等引擎制作和打磨内容；
- 跟进版本落地、测试和体验优化；
- 对任务完成率、流失、选择分布等数据进行分析。

这说明岗位的核心不是“写得好看”本身，而是**对最终玩家体验负责**。文学写作关注文本作品是否成立；游戏叙事还必须回答：

- 玩家是否会按预期顺序看到信息？
- 玩家是否可能在剧情前先杀死 NPC、离开区域或触发另一个系统？
- 分支后状态是否一致？
- 任务目标是否和情节动机一致？
- 台词是否能在 UI、配音时长和镜头节奏中成立？
- 资源成本是否允许？
- 本地化后是否仍然能正常排版和演出？
- 版本更新后旧存档是否会坏？

## 2.2 常见岗位拆分

| 岗位名 | 主要问题 | 典型产出 | 技术深度 |
|---|---|---|---|
| 世界观/文案策划 | 世界为何这样运转，术语如何统一 | 世界观圣经、词汇表、势力/历史/地理设定、系统包装 | 低到中 |
| 剧情策划/游戏编剧 | 人物经历什么、情绪如何变化 | 大纲、分集、场次、对白、角色弧 | 低到中 |
| 任务策划/内容策划 | 玩家具体做什么、如何进入与结束 | 任务流程图、目标、触发器、分支、奖励、引导 | 中到高 |
| 叙事演出策划 | 内容如何被看见和听见 | 分镜、镜头表、场面调度、动作/表情/音频需求 | 中到高 |
| 关卡叙事/环境叙事 | 空间、探索与故事如何互相证明 | 关卡叙事点、拾取物、环境线索、触发区设计 | 中到高 |
| 技术叙事/叙事工具策划 | 写作者如何高效、安全地落地内容 | 数据结构、编辑器、导入器、校验器、命令接口 | 高 |
| 本地化/文本编辑/监修 | 多语言、术语、风格和上下文是否准确 | 本地化主表、上下文、术语库、审校记录 | 中 |
| 内容合规/出版对接 | 版本内容是否满足出版与运营要求 | 审读材料、全量脚本、修改记录、截图/演示材料 | 中 |

实际组织中，岗位名与职责并不一一对应。一个“文案策划”可能负责全部任务配置；一个“任务策划”可能几乎不写对白；一个“叙事策划”可能负责 UE 灰盒和 Sequencer 演出。

## 2.3 团队规模决定职责深度

### 小型团队

一个叙事负责人可能同时完成世界观、大纲、对白、任务图、Unity/UE 配置、简单镜头和测试。优点是决策快，缺点是知识集中、工具薄弱、容易形成个人不可替代性。

### 中型项目

常见做法是“叙事负责人 + 若干剧情/任务策划 + 共享演出/关卡/程序支持”。剧情策划拥有内容，任务策划拥有交互流程，演出策划拥有镜头和场面调度。

### 大型或长线运营项目

会形成内容生产线：

- 叙事总监/主策确定方向；
- 世界观、主线、角色、活动、任务、演出按模块分工；
- 内容制作人管理排期、依赖和冻结点；
- 工具程序维护数据库、导出、预览、审校和自动化；
- 配音、本地化、QA、合规从早期就进入流程。

2026 年 GDC 公开的《恋与深空》过场管线案例尤其说明，大规模长线叙事需要让创作意图尽量独立于底层引擎细节，同时通过专用工具、标准化协作和自动化审阅让上百名艺术家持续交付内容。

# 3. 两条同时运行的生产流程

商业项目不是单一瀑布流程，而是两条嵌套循环。

## 3.1 宏观：项目生命周期

| 宏观阶段 | 叙事工作的核心任务 | 主要里程碑 |
|---|---|---|
| 概念/立项 | 证明题材、角色和玩法能够形成差异化体验 | Narrative Pitch、叙事支柱、风险清单 |
| 前期制作 | 建立世界、角色、主线框架与工具原型 | 世界观圣经、主线 Beat Map、数据原型 |
| 垂直切片 | 用一段接近最终品质的内容证明全管线 | 可玩的代表任务、完整演出、配音/本地化试跑 |
| 全量制作 | 批量生产主线、支线、角色、活动和环境叙事 | Content Complete 前的持续版本交付 |
| Alpha/Beta | 修复逻辑、资源、节奏、本地化、性能和合规问题 | Narrative Lock、VO Lock、Loc Lock |
| 上线 | 准备全量脚本、审查材料、热修与回滚 | 发布候选版本、内容审计通过 |
| 长线运营 | 依据数据和玩家反馈迭代赛季、活动与角色内容 | 版本复盘、下一周期内容计划 |

## 3.2 微观：单条任务/单场剧情的生产循环

单条内容通常经历：

**需求进入 → 叙事意图 → 交互流程 → 文本/演出设计 → 数据化 → 灰盒 → 资源生产 → 合入 → QA → 冻结 → 上线 → 数据复盘**。

两条流程同时运行：项目可能处于“全量制作”，但某一任务刚进入概念，另一任务已在配音，第三任务正进行合规修改。

# 4. 端到端流程：每个阶段的输入、工作、产出和验收

下面给出一套适用于 RPG、开放世界、MMO、二次元长线和剧情向动作游戏的综合流程。小项目可以合并阶段，但不应省略其要回答的问题。

## 阶段 0：商业与产品约束进入

**输入**

- 产品定位、目标用户、平台、商业模式；
- 核心玩法循环和系统框架；
- IP 授权边界、题材限制和发行地区；
- 项目预算、人数、档期、版本节奏；
- 技术栈、目标设备、性能和包体约束；
- 出版、未成年人保护、内容审查和品牌要求。

**核心工作**

- 把抽象商业目标转换为叙事目标；
- 确定内容体量、演出等级和配音范围；
- 识别高风险内容：历史、宗教、现实政治、未成年人、暴力、商业化表达、跨文化歧义等；
- 明确哪些内容是“必须有”、哪些是“可砍”、哪些是“实验”。

**产出**

- 叙事立项简报 Narrative Brief；
- 目标体验和非目标体验；
- 内容预算表；
- 风险与假设清单；
- 初始里程碑和冻结点。

**验收门槛**

- 叙事目标能用玩家行为或体验描述，而不是只有题材口号；
- 内容规模与资源、档期基本匹配；
- 核心玩法和叙事没有根本冲突。

---

## 阶段 1：叙事支柱、主题研究与事实核查

**输入**

- 产品简报；
- 玩法原型；
- 市场、用户和竞品研究；
- IP、历史、文化、科学或职业资料。

**核心工作**

- 提炼 3—5 个叙事支柱，例如“身份伪装”“代价明确的选择”“温暖而非拯救式关系”；
- 明确题材承诺：玩家进入这个世界后，能持续获得什么独特体验；
- 建立事实、文化和敏感内容的研究档案；
- 制定叙事语气、幽默边界、暴力尺度和情感强度。

**产出**

- Narrative Pillars；
- 主题陈述与反主题；
- 研究书目、专家咨询记录、事实核查表；
- 语气与内容边界指南。

**验收门槛**

- 每个支柱能在玩法、任务、角色和美术中被观察到；
- 研究材料可追溯，关键事实不依赖个人记忆。

---

## 阶段 2：世界观、角色与词汇体系

**输入**

- 叙事支柱；
- 玩法系统；
- 美术方向；
- 地图和关卡规划。

**核心工作**

- 建立世界的因果规则，而不只是百科资料；
- 说明经济、技术、魔法、制度、地理、势力如何影响玩家行为；
- 为角色设计欲望、恐惧、矛盾、关系和可被玩法验证的特征；
- 把系统名、物品名、职业名、UI 文案统一到同一语义体系。

**产出**

- 世界观圣经 World Bible；
- 时间线、地理/势力关系图；
- 角色圣经 Character Bible；
- 命名规范、术语库、禁用词和易混词；
- 美术/音频概念需求。

**验收门槛**

- 世界规则能够解释核心玩法；
- 角色设定可以生成行动和冲突，不是只有外貌与履历；
- 同一概念在剧情、系统、UI、市场和本地化中有统一名称。

---

## 阶段 3：宏观叙事架构

**输入**

- 世界与角色设定；
- 主玩法循环；
- 地图/章节结构；
- 商业版本节奏。

**核心工作**

- 设计主线、角色线、支线和赛季线的层级关系；
- 把故事节拍与玩家成长、地图开放、Boss、系统解锁对齐；
- 确定信息释放顺序、伏笔、回收与可选内容；
- 识别分支会造成的永久状态差异和后续成本。

**产出**

- 主线大纲；
- Beat Map/章节图；
- 角色弧和关系变化表；
- 信息揭示矩阵；
- 内容依赖图；
- 分支成本评估。

**验收门槛**

- 每个关键节拍都有相应玩家行动，而不是连续观看；
- 玩法节奏、探索节奏和情绪节奏不存在长时间互相抵消；
- 后续版本能承受已承诺的分支状态。

---

## 阶段 4：内容地图、拆包与产能规划

**输入**

- 宏观剧情架构；
- 关卡/地图计划；
- 资源报价和排期；
- 版本发布日期。

**核心工作**

- 把大纲拆成可独立制作、测试和交付的内容单元；
- 为每个单元标注演出等级、配音范围、角色、场景和技术需求；
- 估算文本量、镜头数、动作数、配音分钟数、本地化字数；
- 规划“最小可交付版本”和砍减顺序。

**产出**

- Content Map；
- 任务/场次清单；
- 资产需求矩阵；
- 产能、依赖和风险表；
- 内容优先级与砍减方案。

**验收门槛**

- 每项内容有 Owner、截止点和依赖；
- 高成本演出有明确价值，不以“重要剧情”作为唯一理由；
- 被砍内容不会破坏主线因果。

---

## 阶段 5：任务与交互叙事设计

**输入**

- 内容单元简报；
- 关卡灰盒；
- 系统能力清单；
- 角色与剧情目标。

**核心工作**

- 定义玩家动词：调查、追踪、谈判、潜入、护送、战斗、选择等；
- 设计任务状态、触发、目标、完成、失败、重试与异常路径；
- 把叙事动机绑定到可观察的玩家行为；
- 设计分支、条件、奖励、回流和后续状态；
- 与关卡、系统、UI、数值共同完成可玩流程。

**产出**

- Quest Brief；
- 状态机/流程图；
- 节点表和条件表；
- 目标、提示、奖励和失败处理；
- 关卡触发器与 NPC 行为需求；
- 埋点方案。

**验收门槛**

- 正常路径、失败路径、取消路径、重复进入和旧存档路径均有定义；
- 任务目标与剧情动机一致；
- 所有条件和命令可以由现有系统实现，或已形成明确技术需求；
- 分支覆盖量可测试、可维护。

---

## 阶段 6：剧本、对白与演出设计

**输入**

- 已批准的任务流程；
- 角色语气规范；
- 演出等级和资源预算；
- 镜头、动画、音频系统能力。

**核心工作**

- 写场景目标、冲突、转折和退出点；
- 产出对白、旁白、系统提示、选择文本、战斗喊话和环境文本；
- 标注情绪、动作、镜头、声音和停顿意图；
- 控制文本长度、信息密度和配音时长；
- 进行桌读、编辑和多人评审。

**产出**

- 场次稿/对白稿；
- Line ID 级台词表；
- 分镜、镜头表或 Previs；
- 表情/动作/音频需求；
- 配音录制稿；
- 文本上下文和本地化备注。

**验收门槛**

- 每一场都有明确的进入状态和退出状态；
- 台词不是承担本应由玩法、画面或环境表达的信息；
- 选择文本能准确预示选择意图；
- 文本长度适配 UI、字幕和镜头；
- 可录制、可翻译、可追踪到稳定 ID。

---

## 阶段 7：技术叙事设计与数据化

**输入**

- 任务流程、台词和演出稿；
- 引擎数据结构；
- 本地化、配音和资产命名规范；
- 存档与版本兼容要求。

**核心工作**

- 把自然语言内容转为结构化数据；
- 确定节点类型、条件类型、命令类型和参数；
- 分配稳定 ID；
- 建立外部创作工具与引擎之间的导入/导出规则；
- 编写自动校验：重复 ID、断链、缺文本、缺资产、死分支、不可达节点等。

**产出**

- 数据字典与 Schema；
- 中间格式 JSON/CSV/Yarn/Ink/自研 DSL；
- 命令 API 契约；
- 变量所有权表；
- 导入器、导出器和校验规则需求；
- 版本迁移规则。

**验收门槛**

- 内容可以无人工复制地进入引擎，或人工步骤有严格检查；
- 任何节点都可由 ID 搜索、预览和定位；
- 逻辑不隐藏在备注、台词或镜头轨道中；
- 导入失败会给出可行动的错误信息。

---

## 阶段 8：引擎灰盒与内容实现

**输入**

- 结构化内容；
- 关卡灰盒；
- 临时角色、UI、音频和动画；
- 引擎运行时系统。

**核心工作**

- 在 UE/Unity 中搭建触发、NPC、任务状态和对白运行；
- 用占位资产完成端到端体验；
- 调整镜头、走位、节奏、交互距离、失败与恢复；
- 让剧情策划能在不依赖完整美术资产的情况下早期试玩。

**产出**

- 可玩的叙事灰盒；
- 初版 Blueprint/C# 配置；
- 临时 Sequencer/Timeline；
- 缺陷、工具和资产需求清单；
- 体验评审录像或可复现 Build。

**验收门槛**

- 从触发到结束可完整运行；
- 所有关键状态可调试查看；
- 异常离开、死亡、断线、跳过、重复触发有合理处理；
- 设计意图在没有最终资产时已经成立。

---

## 阶段 9：正式资产、配音、本地化与演出合入

**输入**

- 经验证的灰盒；
- 锁定或接近锁定的台词；
- 美术、动画、音频、VFX、镜头资产；
- 本地化译文与配音文件。

**核心工作**

- 将占位资产替换为最终资产；
- 管理配音、口型、字幕、时长和多语言版本；
- 在 Sequencer/Timeline 中完成镜头、动画、声音和事件；
- 对不同设备、帧率、语言和跳过策略进行适配；
- 管理晚期改词对配音、本地化和镜头的连锁影响。

**产出**

- 最终或发布候选演出；
- VO 资产与映射表；
- 多语言 String Table/Localization Table；
- 资源状态和缺失报告；
- 变更影响清单。

**验收门槛**

- 文本、配音、口型、字幕与镜头一致；
- 所有语言无截断、乱码、错误占位符；
- 资产引用和加载策略满足性能、包体与热更要求；
- 跳过和快进不会破坏任务状态。

---

## 阶段 10：叙事 QA、内容审读与合规

**输入**

- 发布候选版本；
- 全量脚本、术语库、任务图和资产清单；
- 出版与公司内部内容标准。

**核心工作**

- 逻辑测试、分支覆盖、存档兼容、断线/重连测试；
- 文本审校、事实核查、角色一致性和连续性检查；
- 本地化 Linguistic QA；
- 内容敏感项、命名、未成年人和商业化表达审查；
- 生成出版所需的全量中文脚本、截图、演示和修改记录。

**产出**

- Narrative QA Matrix；
- 分支覆盖报告；
- 文本/本地化缺陷单；
- 审读报告与修改记录；
- 全量中文脚本、屏蔽词库及辅助材料；
- 发布签署记录。

**验收门槛**

- P0/P1 逻辑问题清零；
- 全量文本可导出、可检索、可追溯；
- 版本内容与申报/审核版本一致；
- 后续热修有回滚方案。

国家新闻出版署的国产网络游戏审批材料明确要求提交游戏中所有中文字符合集，包括系统提示、NPC 对话、任务情节、道具名称等，以及游戏屏蔽词库。这意味着“全量文本可导出”不是锦上添花，而应从数据架构初期就成为硬要求。

---

## 阶段 11：上线、数据观察与长线迭代

**输入**

- 上线版本；
- 任务和叙事埋点；
- 客服、社区、舆情和商店评价；
- 崩溃、卡死和存档数据。

**核心工作**

- 监控任务开始率、完成率、放弃点、选择分布、跳过率；
- 区分“玩家不喜欢”与“玩家看不懂/无法完成/性能阻断”；
- 对高流失节点进行文案、目标、引导、关卡或难度联合优化；
- 记录世界状态和角色连续性，避免长线版本自相矛盾；
- 管理热修、回滚和旧存档迁移。

**产出**

- 版本叙事复盘；
- 数据看板；
- 玩家理解问题清单；
- 下一版本假设与实验；
- Canon/连续性更新；
- 迁移与热修脚本。

**验收门槛**

- 数据解释结合定性反馈，不把完成率直接等同于剧情质量；
- 所有修改有版本号、影响范围和回归测试；
- 长线新增内容不破坏已发布状态。

# 5. 剧情策划的核心文档与字段模板

## 5.1 Narrative Brief

建议至少包含：

- 内容 ID、版本、Owner；
- 玩家体验目标；
- 目标用户与前置认知；
- 核心冲突和情绪曲线；
- 玩法动词；
- 进入/退出世界状态；
- 必须传达的信息；
- 不应传达的信息；
- 资源预算与演出等级；
- 合规/文化/事实风险；
- 成功指标；
- 可砍内容。

## 5.2 世界观圣经

不要只写百科，应优先写“规则与后果”：

- 世界核心规律；
- 制度、经济、技术/魔法怎样改变普通人的生活；
- 各势力拥有、缺乏和争夺什么；
- 玩家为何能够进行核心玩法；
- 禁区、例外和故意保留的未知；
- 术语定义、别名、禁用名；
- 已发布 Canon 与尚可修改内容的边界。

## 5.3 角色圣经

建议字段：

- CharacterID；
- 表层目标、深层需求、恐惧、错误信念；

- 公开信息、秘密和谎言；
- 与玩家关系的状态机；
- 语言特征、禁用表达、称谓规则；
- 可用动画、表情、语音和战斗能力；
- 角色弧关键节点；

# 6. 从自然语言稿件到可执行内容

## 6.1 推荐的分层架构

```text
创作层
  Docs / Sheets / Ink / Yarn / Twine / articy / 自研编辑器
          ↓
规范化与校验层
  Schema 校验、ID 分配、条件检查、断链检查、字数与资源检查
          ↓
中间格式
  JSON / CSV / 二进制编译结果 / 自研数据包
          ↓
引擎导入层
  UE DataTable/DataAsset/StringTable 或 Unity ScriptableObject/Localization Table
          ↓
运行时
  Quest State Machine / Dialogue Runner / Narrative Subsystem
          ↓
表现层
  UI、角色、动画、摄像机、Sequencer/Timeline、音频、VFX、关卡事件
          ↓
持久化与观测
  Save、Telemetry、Debug Overlay、日志、版本迁移
```

## 6.2 三种常见工作模式

### 引擎内创作

剧情策划直接在 UE/Unity 的节点编辑器、DataTable、Inspector 或自研面板中编辑。

**优点**：所见即所得、资产引用方便、无需导入。  
**缺点**：二进制资源难 Diff/Merge；大量文本编辑体验差；本地化、审读和外包协作成本高。

适合内容量较小、团队集中、强演出导向的项目。

### 外部工具创作

主要内容在 Sheets、Ink、Yarn、Twine、articy 或数据库中，导入引擎。

**优点**：文本和分支易编辑；版本对比、多人协作和本地化更友好。  
**缺点**：必须投入导入、校验、预览和资产映射工具。

适合文本量大、分支多、语言多或多人写作项目。

### 混合模式——商业项目通常最稳妥

- **剧情语义、台词、任务状态和稳定 ID**在外部单一真源维护；
- **关卡绑定、角色实例、镜头、动画和实时演出**在引擎中维护；
- 两者通过稳定 ID、命令和资产映射表连接。

这样可以避免两个极端：既不会把大量文本锁在二进制引擎资产里，也不会让外部文档脱离真实游戏。

## 6.3 四种接口契约

### 身份契约

统一命名示例：

```text
QST_CH02_030
QST_CH02_030_N010
LINE_QST_CH02_030_N010_001
SEQ_QST_CH02_030_INTRO
VO_ZH_LINE_QST_CH02_030_N010_001
```

ID 一旦进入配音、本地化、存档或埋点，就不应因改文案而变化。

### 状态契约

建立变量所有权表：

| 变量 | 类型 | Owner | 可写者 | 持久化 | 说明 |
|---|---|---|---|---|---|
| `quest.qst_030.state` | Enum | Quest System | Quest Runner | 是 | 任务主状态 |
| `story.mei_trust` | Int | Narrative | Dialogue/Quest | 是 | 角色关系 |
| `world.bridge_destroyed` | Bool | World System | Level Event | 是 | 世界永久状态 |
| `combat.boss_phase` | Int | Combat | Combat | 否 | 战斗临时状态 |

剧情工具不应随意写入所有系统变量。跨系统写入应通过命令或服务接口完成。

### 命令契约

剧情脚本只表达“意图”，由引擎执行：

```text
sequence.play(sequenceId="SEQ_QST_030_INTRO")
quest.set_objective(objectiveId="OBJ_FIND_CLUE")
flag.set(flag="story.mei_knows_truth", value=true)
item.grant(itemId="ITEM_LETTER", count=1)
npc.move(npcId="NPC_MEI", markerId="MK_WINDOW")
audio.play(eventId="BGM_TENSION_A")
telemetry.emit(eventId="QST_030_CHOICE", value="TELL_TRUTH")
```

推荐使用有类型参数或可验证 DSL，而不是任意字符串命令。

### 资产契约

剧情数据引用逻辑资产键，项目资产系统再映射到真实资源：

```text
CharacterID -> Prefab/Blueprint/Actor Class
EmotionTag  -> Facial Pose/Animation State
SequenceID  -> Level Sequence/Timeline Asset
AudioEvent  -> Wwise/FMOD/AudioClip/SoundWave
TextKey     -> String Table/Localization Table
```

这允许替换资产而不改剧情数据，也能支持不同平台和语言版本。

# 7. 对接 Unreal Engine 的典型方式

## 7.1 数据层

### DataTable

适合大批量、结构统一的行式数据，例如任务节点、对白索引、奖励和配置。UE 官方支持从 CSV 导入到与行结构对应的 DataTable，并可重新导入更新。

推荐用途：

- `FQuestRow`：任务基础数据；
- `FDialogueLineRow`：LineID、SpeakerID、TextKey、标签；
- `FQuestNodeRow`：节点类型、条件、后继节点；
- `FAssetMappingRow`：逻辑 ID 到 Soft Object Path。

不建议把复杂嵌套分支硬塞入一张巨大 DataTable；可把表用于索引，复杂结构放 JSON、DataAsset 或编译后的自研资产。

### DataAsset / PrimaryDataAsset

适合包含复杂结构、软资产引用、编辑器友好字段和资源包管理的内容。可为每条任务生成一个 `UQuestDefinition`（项目自定义类）或每个章节生成一个 Primary Data Asset。

推荐用途：

- 一条任务的完整 Definition；
- 角色叙事配置；
- 章节内容包；
- Sequence、音频、角色和 UI 资源 Bundle。

### FText 与 String Table

所有面向玩家的文本应进入本地化体系。使用稳定 TextKey 连接源文本、译文、字幕和 UI，不要在 Blueprint、Sequencer 或任务表中散落硬编码 FString。

### Gameplay Tags

可把层级标签用于状态、条件和内容分类，例如：

```text
Story.Ch02.Mei.Trust.High
Quest.QST_030.Completed
World.Area.Harbor.Alerted
Narrative.Emotion.Angry
Narrative.Command.Sequence.Play
```

Gameplay Tags 适合查询和组合，不应替代所有有数值含义的变量。

## 7.2 运行时层

商业项目通常自建或引入：

- Quest Subsystem/Manager；
- Dialogue Runner；
- Narrative Variable Store；
- Condition Evaluator；
- Command Dispatcher；
- Save Migration；
- Debug UI。

运行时的职责是：

1. 读取节点；
2. 校验进入条件；
3. 输出台词、选择或目标；
4. 等待玩家/游戏事件；
5. 执行命令；
6. 写入状态和存档；
7. 移动到下一个节点。

剧情策划应能在编辑器中看到当前 QuestID、NodeID、变量、最近命令和错误，而不是只依赖日志文本。

## 7.3 表现层

### Blueprint

Blueprint 适合：

- 关卡触发器；
- NPC 交互；
- 接收 Narrative Command；
- 控制 UMG 对话界面；
- 绑定动画、音频和 Sequence；
- 快速搭建灰盒。

量产时应避免每条任务复制一套巨大 Blueprint。公共逻辑应下沉到组件、子系统、数据驱动节点和函数库。

### Sequencer / Level Sequence

适合确定时间轴的镜头、角色动画、声音和事件。建议把 Sequencer 当作**表现资产**，而不是剧情状态的唯一真源。

正确边界：

- Narrative Runner 决定是否进入某段演出；
- Sequence 播放镜头、动画、声音和有限事件；
- Sequence 结束后向 Narrative Runner 返回明确结果；
- 跳过时由 Runner 写入同样的最终状态。

错误做法是把关键任务逻辑只藏在 Sequencer Event Track 中，导致跳过、重播、存档和多人同步难以维护。

### SaveGame

任务状态、关键变量、已看节点、分支选择和世界永久状态需要进入项目的存档模型。ID 重命名或数据结构变化时要有迁移表。

## 7.4 UE 推荐导入流程

```text
剧情数据库/Sheets/Ink/Yarn/articy
        ↓ Export
规范化 JSON/CSV + Localization CSV
        ↓ CI/Editor Importer
DataTable + DataAsset + StringTable
        ↓ Validate
重复 ID / 断链 / 缺资产 / 无法到达 / 未本地化
        ↓ Runtime
QuestSubsystem + DialogueRunner + CommandDispatcher
        ↓ Presentation
UMG + Actor/AI + Sequencer + Audio + VFX
```

## 7.5 UE 自动校验建议

利用项目自定义 Validator 或命令行工具检查：

- ID 唯一；
- NextNode 存在；
- 所有非终止节点有后继；
- 任务至少有一个可达结束；
- TextKey 存在且源语言非空；
- SequenceID、角色、动画、音频可解析；
- 条件变量已注册且类型正确；
- 命令名称与参数 Schema 匹配；
- 发布内容不引用 Development/Test 资产；
- 修改后的 Changelist 不产生断链。

UE 的 Data Validation 子系统支持在 UI、保存或命令流程中运行项目特定验证器，适合把这些检查放进提交前和 CI。

# 8. 对接 Unity 的典型方式

## 8.1 数据层

### ScriptableObject

Unity 官方将 ScriptableObject 定义为独立于场景实例的数据容器。叙事系统常将每条任务、角色、章节或对话项目导入为 ScriptableObject 资产。

示例项目自定义类：

```text
QuestDefinition : ScriptableObject
DialogueProject : ScriptableObject
CharacterNarrativeProfile : ScriptableObject
NarrativeAssetMap : ScriptableObject
```

优点是 Inspector 友好、可引用其他 Unity 资产；缺点是大量文本和多人合并体验未必理想。因此仍建议外部文本真源 + 自动生成/更新 ScriptableObject。

### JSON/CSV

适合远程内容、快速迭代或保持文本可 Diff。导入后可直接运行，也可在 Editor 阶段编译成 ScriptableObject 或二进制数据。

### Unity Localization String Tables

使用 Key/ID 获取不同 Locale 的字符串。官方 Localization 包支持字符串和资产本地化、伪本地化，以及 CSV、XLIFF、Google Sheets 导入导出。剧情策划应为译者提供角色、场景、变量含义、字符限制和语气上下文。

## 8.2 运行时层

常见选择：

- 自研 Quest/Dialogue Runner；
- Ink Runtime；
- Yarn Spinner；
- 其他节点图或视觉小说框架。

运行时一般由 MonoBehaviour 或纯 C# 服务包装。不要让 UI 直接解析所有剧情逻辑；建立清晰的 Presenter/Runner/State Store 分层。

## 8.3 表现层

### Timeline 与 PlayableDirector

Timeline 用于影片内容、游戏序列、音频和复杂效果。典型做法：

- Timeline Asset 保存轨道和 Clip；
- 场景中的 PlayableDirector 负责绑定真实 GameObject；
- Signal 或自定义 Playable 在时间点向游戏系统发事件；
- Narrative Runner 负责开始、结束、跳过和状态提交。

同样，不应让关键剧情状态只存在于 Timeline 的 Signal 中。

### UI、动画与音频

Dialogue Presenter 把 LineID/TextKey 解析为：

- 本地化文本；
- 角色头像/立绘/模型；
- 表情或 Animator 参数；
- 音频事件；
- 字幕时长与自动推进策略。

### Addressables

可把章节、角色、语音和演出资产按地址异步加载，并支持本地或远程内容。Narrative Asset Map 只保存 Addressable Key，避免剧情数据直接持有大量硬引用。

## 8.4 Unity 推荐导入流程

```text
Ink/Yarn/Sheets/自研编辑器
       ↓
JSON/CSV/编译结果 + Localization 数据
       ↓ AssetPostprocessor / EditorWindow / CI
ScriptableObject + String Tables + Addressable Keys
       ↓ Validate
ID / 分支 / Key / Asset / Locale / Command
       ↓ Runtime
QuestService + DialogueRunner + VariableStore
       ↓ Presentation
UI Toolkit/uGUI + Animator + Timeline + Audio
```

## 8.5 Unity 校验建议

- 通过 Editor Script 在导入时生成报告；
- 在 Build 前阻断缺失 TextKey、重复 ID 和无效 Addressable Key；
- 为 Ink/Yarn 的命令建立注册表，禁止未处理命令进入发布版本；
- 对 Timeline 绑定和 Signal Receiver 做场景级检查；
- 对所有 Locale 运行伪本地化和 UI 截断测试；
- 在 Play Mode 提供跳转到指定 QuestID/NodeID 的调试入口。

# 9. UE 与 Unity 对照表

| 叙事需求 | Unreal Engine 常用实现 | Unity 常用实现 |
|---|---|---|
| 批量结构化配置 | DataTable/CSV | CSV/JSON、生成 ScriptableObject |
| 复杂内容资产 | DataAsset/PrimaryDataAsset | ScriptableObject |
| 本地化文本 | FText、String Table、Localization Dashboard | Localization String Tables |
| 状态标签 | Gameplay Tags | Enum、常量、ScriptableObject Tag 或自研 Tag 系统 |
| 对话/任务运行 | Blueprint/C++ 自研或插件 | C# 自研、Ink、Yarn Spinner |
| 过场演出 | Sequencer/Level Sequence | Timeline/PlayableDirector |
| 时间轴事件 | Event Track/Blueprint/C++ 接口 | Signal/Receiver、自定义 Playable |
| UI | UMG/Common UI | uGUI/UI Toolkit |
| 存档 | USaveGame/项目存档服务 | 自研序列化/项目存档服务 |
| 资产加载 | Asset Manager、Primary Asset、Soft Reference | Addressables |
| 编辑器校验 | Data Validation、Editor Utility/Python/C++ | Editor Script、AssetPostprocessor、Tests |
| 版本协作 | Perforce/Git；注意二进制资产锁定 | Git/Plastic/Perforce；注意 Scene/Prefab 冲突 |

结论不是“哪个引擎更适合剧情”，而是：

- UE 对大型实时演出、Sequencer、Blueprint 和资产管理提供强集成；
- Unity 更容易围绕 C#、文本格式和开源运行时快速建立轻量工具链；
- 两者都需要项目自行定义任务状态、命令、存档、校验和本地化工作流；
- 引擎自带的时间轴都不是完整的叙事数据库或任务系统。

# 10. 一个任务从设计到引擎的完整示例

## 10.1 任务概念

**QuestID**：`QST_A01_020`  
**名称**：失联的驿使  
**体验目标**：玩家通过观察环境和与两名 NPC 对话，判断驿使是被袭击还是主动失踪；选择是否向守卫隐瞒真相。

## 10.2 进入和退出状态

**进入条件**

```text
Quest.Intro.Completed == true
World.Area.Riverside.Unlocked == true
QST_A01_020.State == NotStarted
```

**退出状态 A：报告真相**

```text
QST_A01_020.State = Completed
Story.GuardTrust += 1
Story.CourierSecretKnown = true
World.CourierWanted = true
```

**退出状态 B：隐瞒**

```text
QST_A01_020.State = Completed
Story.CourierSecretKnown = true
World.CourierWanted = false
Story.CourierTrust += 1
```

## 10.3 节点图

```text
N000 Start
  -> N010 与守卫对话
  -> N020 调查三个线索（可并行）
       N021 断裂的箭
       N022 被撕掉的制服标记
       N023 河岸脚印
  -> N030 汇总结论
  -> N040 Choice
       C1 报告真相 -> N050A
       C2 隐瞒真相 -> N050B
  -> N090 End
```

## 10.4 台词数据

```csv
LineID,NodeID,SpeakerID,TextKey,EmotionTag,AudioEventKey,NextNodeID
LINE_QST_A01_020_001,N010,NPC_GUARD,LOC_LINE_QST_A01_020_001,Concerned,VO_LINE_QST_A01_020_001,N011
LINE_QST_A01_020_002,N030,PLAYER,LOC_LINE_QST_A01_020_002,Thinking,,N040
```

## 10.5 命令

```text
N010.OnExit:
  quest.set_objective("OBJ_FIND_3_CLUES")
  telemetry.emit("QST_A01_020_INVESTIGATION_START")

N040.C1:
  flag.set("World.CourierWanted", true)
  relation.add("Story.GuardTrust", 1)
  sequence.play("SEQ_QST_A01_020_REPORT")

N040.C2:
  flag.set("World.CourierWanted", false)
  relation.add("Story.CourierTrust", 1)
  sequence.play("SEQ_QST_A01_020_HIDE")
```

## 10.6 UE 落地

- `QST_A01_020` 作为 `UQuestDefinition` DataAsset 或任务索引 DataTable 行；
- 节点数据由 JSON 导入为 DataAsset/运行时数据；
- `TextKey` 进入 String Table；
- 条件由 Gameplay Tags + Typed Variable Store 解析；
- 线索 Actor 上放置 `QuestInteractableComponent`，完成后发出 Objective Event；
- `sequence.play` 由 Command Dispatcher 解析并加载 Level Sequence；
- Sequence 完成或跳过后回调 Runner，Runner 再提交最终状态；
- `USaveGame` 保存 QuestState、已发现线索和最终选择；
- Data Validator 检查两个 Sequence、所有 TextKey 和三个线索 ID 均存在。

## 10.7 Unity 落地

- 导入为 `QuestDefinition` ScriptableObject；
- 对话可在 Yarn/Ink 中编写，或使用自研 Node 数据；
- `TextKey` 进入 Localization String Table；
- 三个线索 GameObject 挂接 `QuestObjectiveEmitter`；
- `sequence.play` 映射到 Addressable Timeline Asset 和 PlayableDirector；
- Signal 只触发表现事件，最终状态由 QuestService 提交；
- 存档保存 QuestID、NodeID、Objective Set 和选择；
- Editor Validator 检查 Localization Key、Timeline Address 和命令处理器。

## 10.8 QA 用例

- 只调查一个或两个线索时是否允许结论；
- 先发现线索后再接任务；
- 调查中死亡或传送；
- 快速连续交互导致重复计数；
- 选择界面打开时断线；
- 跳过两个不同结局 Sequence；
- 完成后再次与守卫交谈；
- 旧存档中缺少新增变量时的默认值；
- 所有语言下选择按钮是否截断；
- 两个选择的埋点和后续世界状态是否一致。

# 11. 跨团队对接与 RACI

| 工作项 | 叙事负责人 | 剧情/任务策划 | 关卡 | 程序 | 演出/动画 | 音频 | 本地化 | QA | 制作人 |
|---|---|---|---|---|---|---|---|---|---|
| 叙事支柱 | A | R/C | C | C | C | C | C | I | C |
| 任务流程 | C | A/R | R | C | C | I | I | C | C |
| 数据 Schema | C | R | C | A/R | C | I | C | C | C |
| 引擎灰盒 | C | R | R | R | C | I | I | C | A |
| 最终演出 | A/C | R | C | C | A/R | R | C | C | C |
| 配音锁定 | A | R | I | I | C | A/R | C | C | C |
| 本地化锁定 | A/C | R | I | C | C | C | A/R | R | C |
| 合规审读 | A | R | I | I | C | C | C | R | C |
| 上线签署 | C | R | R | R | R | R | R | R | A |

A = Accountable，R = Responsible，C = Consulted，I = Informed。

关键不是表格本身，而是避免出现：

- “所有人都以为别人会检查”；
- “剧情策划负责体验，但没有修改引擎内容的权限”；
- “程序负责工具，却不知道写作者的真实工作流”；
- “配音和本地化直到最后才看到完整上下文”；
- “改了一句台词，却没有人知道要重录、重做口型和重审字幕”。

# 12. 评审与冻结机制

## 12.1 建议的评审门

### Gate A：叙事意图批准

检查玩家体验、主题、角色动机和玩法关系。

### Gate B：流程批准

检查任务状态、异常路径、资源和技术可行性。此时不应沉迷逐句润色。

### Gate C：灰盒批准

实际试玩验证节奏、理解和系统可靠性。未通过前不应大规模制作最终资产。

### Gate D：剧本/VO 锁定

台词进入录制和本地化前，完成编辑、桌读、上下文和发音检查。

### Gate E：内容完成

最终资产合入，允许 Bug 修复，不再扩大范围。

### Gate F：发布签署

逻辑、本地化、性能、合规、存档迁移和回滚均通过。

## 12.2 冻结不是“从此一字不改”

冻结应定义变更成本：

- **文本冻结前**：常规编辑；
- **配音后**：改词需说明是否重录、拼接或只改字幕；
- **口型/镜头后**：改词需评估时长和动画；
- **申报/审核后**：重要内容变化需要出版与法务/合规评估；
- **上线后**：需兼容旧存档和已产生的玩家状态。

建议每次变更记录：原因、Owner、受影响 ID、资产、本地化语言、录音、镜头、测试和审批状态。

# 13. 中国大陆商业项目的特殊约束

## 13.1 出版和全量内容可追溯

国家新闻出版署的国产网络游戏审批事项要求包括：

- 游戏作品符合出版、互联网信息服务和网络出版相关规定；
- 提交游戏画面截图和审查辅助材料；
- 提交游戏作品中文脚本全文与屏蔽词库；
- 脚本全文覆盖系统提示、NPC 对话、任务情节、道具名称等所有中文字符；
- 审查版本须与出版版本一致。

对叙事管线的工程含义是：

1. 所有玩家可见文本必须进入可导出的统一体系；
2. 不应把大量文字硬编码在临时 Blueprint、Prefab、贴图或视频里；
3. 每次版本构建应能生成全量文本快照和差异；
4. 内容审读和修改记录应关联 TextKey/LineID；
5. 活动和热更内容也要进入同一审计流程。

## 13.2 价值导向、文化与事实质量

国家新闻出版署关于网络游戏精品出版工程的通知强调把正确价值取向融入主线剧情和玩法规则、加强选题论证和内容把关、规范语言文字、避免知识性常识性错误。这意味着合规不应只在最终阶段做“敏感词扫描”，而应在选题、世界观、系统包装、任务奖励和商业化表达阶段就参与。

## 13.3 长线运营

中国大陆商业项目中，手游、MMO、赛季制和二次元长线产品占比较高。叙事生产常面对：

- 固定版本发布日期；
- 主线、角色、活动和商业化内容并行；
- 多语言同步或接近同步；
- 频繁配音和演出交付；
- 旧内容无法轻易删除；
- 玩家会长期追踪设定和角色一致性。

因此需要：

- Canon 数据库；
- 角色关系与世界状态台账；
- 版本内容包和依赖管理；
- 快速预览、自动审阅和差异报告；
- 旧存档迁移与回归测试；
- 活动内容结束后的状态回收策略。

# 14. 质量指标与数据使用

## 14.1 叙事质量的六个维度

1. **连贯性**：因果、角色动机、世界规则和时间线一致；
2. **可理解性**：玩家知道发生了什么、为何行动、下一步做什么；
3. **能动性**：玩家行动或选择对体验产生可感知影响；
4. **节奏**：信息、战斗、探索、演出和休息交替合理；
5. **表现一致性**：文本、镜头、动画、音频和玩法指向同一情绪；
6. **生产可靠性**：可测试、可翻译、可版本管理、可修复。

## 14.2 可观测指标

- 任务曝光率、开始率、完成率；
- 各节点停留时长；
- 放弃/失败/卡死位置；
- 选择分布；
- 对话跳过率与重复观看率；
- 引导提示触发次数；
- 任务完成后相关系统使用率；
- 客服关键词、社区误解点；
- 本地化缺陷率；
- 每千行台词缺陷数；
- 每分钟演出的制作成本和返工次数。

这些数据只能回答“发生了什么”，不能单独回答“故事好不好”。例如高跳过率可能来自重复游玩、字幕速度、奖励驱动、镜头过长或剧情不吸引，必须结合访谈、录像、社区语义和任务上下文解释。

# 15. 常见失败模式与修复策略

## 15.1 先写长篇剧本，最后再找玩法承载

**后果**：大量对白、强制演出、玩法与动机脱节。  
**修复**：先定义玩家动词、世界状态变化和内容预算，再写场次。

## 15.2 逻辑藏在台词和备注里

**后果**：程序无法验证，测试无法覆盖，改词可能破坏逻辑。  
**修复**：条件、命令、状态和后继节点必须结构化。

## 15.3 不使用稳定 ID

**后果**：改一句话导致配音、本地化、镜头、埋点和存档失联。  
**修复**：ID 与文本分离，删除也保留 Tombstone/迁移记录。

## 15.4 把 Sequencer/Timeline 当任务系统

**后果**：跳过、重播、存档、分支和异常恢复不可控。  
**修复**：状态由 Runner 管理，时间轴只负责表现并返回结果。

## 15.5 分支爆炸

**后果**：后续内容、配音、测试和本地化指数增长。  
**修复**：区分局部反馈、短期状态和永久世界分支；多使用“差异化表达、有限状态、可控汇流”。

## 15.6 写作者无法即时试玩

**后果**：问题到最终 Build 才暴露，返工昂贵。  
**修复**：文本工具内预览、引擎一键跳节点、自动编译和热重载。

## 15.7 配音、本地化和合规进入太晚

**后果**：晚期改词触发连锁返工，或无法按期上线。  
**修复**：在垂直切片阶段试跑全链路；文本阶段即提供上下文、发音、字符限制和风险标签。

## 15.8 过度依赖人工复制

**后果**：错行、漏行、版本混淆、无法审计。  
**修复**：单一真源、自动导入导出、生成报告、CI 校验。

## 15.9 工具功能很多，但错误信息不可用

**后果**：策划依赖程序排错，效率反而下降。  
**修复**：错误必须包含文件、行号、QuestID、NodeID、原因和建议动作。

# 18. GitHub 工具选型检查表

在商业项目采用任何开源叙事工具前，至少回答：

1. 是否允许商业使用，许可证是否与项目政策兼容？
2. 当前引擎版本是否支持？升级是否需要源码改造？
3. 文本、变量和节点是否有稳定 ID？
4. 是否支持本地化、上下文、复数和多语言资产？
5. 是否支持保存/加载、版本迁移和旧存档？
6. 是否能导出全量中文脚本和差异？
7. 是否支持命令注册和参数校验？
8. 是否能在 CI 中无界面编译和验证？
9. 是否能处理十万行文本、数千节点或多人并行编辑？
10. 是否支持搜索、引用查找、不可达节点和死循环检查？
11. 是否能与配音、口型、字幕和资产状态关联？
12. 工具停止维护后，团队是否有能力接管？
13. 是否存在供应商锁定或不可导出的专有格式？
14. 错误定位是否精确到文件、行、节点和字段？
15. 引擎内表现与外部真源如何避免双向修改冲突？

# 19. 建议的剧情策划作品集

一个能证明“商业落地能力”的作品集，不应只有世界观设定或小说片段。推荐制作一个 10—20 分钟可玩任务，包含：

- 一页 Narrative Brief；
- 世界和角色的最小设定；
- 任务状态图；
- 至少一个局部选择和一个后续状态差异；
- 台词主表与稳定 ID；
- UE 或 Unity 可运行 Build；
- 一段 Sequencer/Timeline 演出；
- 存档、跳过和失败恢复；
- 中文与至少一种伪本地化/第二语言；
- 自动校验报告；
- QA 用例和一次迭代复盘；
- Git 仓库中清晰的 README、数据结构和提交历史。

面试时重点讲清楚：

1. 目标玩家体验；
2. 为什么选择这些玩法动词；
3. 输入、输出和依赖；
4. 如何把剧本转成数据；
5. 如何对接程序、美术、关卡、动画和音频；
6. 遇到什么异常路径；
7. 如何用测试和数据改进；
8. 哪些内容被砍，以及为什么。

# 20. 最终结论

中国大陆商业游戏剧情策划的核心竞争力可以概括为五项：

1. **叙事判断力**：知道什么值得讲、何时讲、用文本还是用玩法/画面讲；
2. **交互设计力**：把故事变成玩家行动、状态变化和反馈；
3. **生产表达力**：把创意写成其他岗位可执行、可报价、可验收的需求；
4. **技术落地力**：理解数据、状态机、命令、资产、本地化、存档和引擎工具；
5. **版本责任感**：能够跟进灰盒、资源、QA、合规、上线和数据迭代，而不是交稿即结束。

最成熟的工作方式不是要求剧情策划成为全职程序员，而是让其理解足够的技术边界，并与工具程序共同建立一套**写作者能高频迭代、程序能稳定执行、制作人能预测成本、QA 能覆盖分支、发行能导出审查材料、玩家能可靠体验**的内容系统。
